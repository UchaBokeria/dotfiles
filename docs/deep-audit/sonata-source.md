## Source concerns and limits

SS007 — `filelock.ts` stale reclamation records inode/mtime/token but rechecks only inode+token after rename. A holder that renews its mtime after a waiter observes a stale lock can still lose it, because the renewal does not change those two checks. This is a narrow race candidate from source, not reproduced; callers and tests remain to be reconciled. Synchronous holders do not renew during their critical section, so an unusually slow >5s sync operation also exceeds the lease assumption.

SS008 — Capability400 counters are described as consecutive identical fingerprints, but when one recognized fingerprint replaces another the previous counter is retained; counters clear only on an unrecognized terminal failure or served response. Thus A/B/A/A can reach A's threshold without three consecutive As. Prefix-based clearing also uses model-name string prefixes rather than a delimited counter key. Scope: fallback classification; not a provider exploit claim.

SS009 — Proxy `readBody()` buffers incoming requests without a byte ceiling; only dashboard write bodies have an explicit cap. Loopback and Host protections narrow access but do not impose a general inference-body memory bound. Source only, no resource exhaustion attempted.

SS010 — Retired-child cleanup in serve removes a retired temp directory and forgets its record even when a still-alive child cannot be positively identified, or `terminatePid()` returns false. Final shutdown similarly ignores termination failure before deleting owned directories. This contradicts the narrower retirement rule for live token directories elsewhere in the same file and can strand an unserviceable process/config identity. Source candidate, helper/tests cross-check pending.
