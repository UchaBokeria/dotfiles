## Architecture rules

- **One compose file** (`compose.yml`, project name `cloud`) for everything except Harbor (which has its own — see [docs/harbor.md](docs/harbor.md)).
- **Traefik terminates all TLS.** Services run plain HTTP internally; never enable per-service HTTPS and never publish host ports — only Traefik binds 80/443.
- **Every service folder has a Dockerfile** that owns the service's config. Compose only wires env/networks/volumes/labels. After editing a baked-in config file: `docker compose up -d --build <service>`.
- Networks: `proxy` (external-facing, shared with Harbor by name), `data` (internal; pgbouncer/minio/redis), `db` (internal; postgres↔pgbouncer only), `nohrpls` (non-internal — background worker needs outbound internet; pins DNS to 1.1.1.1/8.8.8.8), `socket` (internal; traefik↔socket-proxy only).
- **Traefik has no docker.sock mount** — reads the Docker API via `socket-proxy` (GET-only, CONTAINERS+NETWORKS+INFO; writes get 403). CrowdSec reads traefik's logs through it too.
- **Every websecure request passes a middleware chain** (real-IP → crowdsec → secure-headers) — full detail in [docs/crowdsec.md](docs/crowdsec.md).
- All state is bind-mounted inside this tree (`*/data` dirs) so restic backs up one directory.

Adding a web service: folder with Dockerfile → service in `compose.yml` on `proxy` (+ `data` if it needs pg/redis/minio) → traefik labels (Host rule, entrypoints websecure, certresolver `${CERT_RESOLVER:-letsencrypt}`, loadbalancer port) → `docker compose up -d --build`. No DNS/cert step (wildcard record + wildcard cert cover new subdomains) unless it needs big uploads → add a DNS-only (grey cloud) record instead.

## Reboot recovery

This host reboots often. `boot.sh` runs from crontab `@reboot`: waits for the docker daemon, then `docker compose up -d`'s every project in its `PROJECTS` array (cloud stack + Harbor). Add new compose projects to that array. If a domain 404s after reboot, read `boot.log` and `docker ps -a` first. (Harbor doesn't self-recover after reboots — see [docs/harbor.md](docs/harbor.md).)

**The Claude/Telegram session self-heals too**: `telegram/poller-watchdog.sh` runs from crontab every 5 min — restarts the session if tmux or the `bun server.ts` poller is gone (3-miss delay + 30-min cooldown, because a restart wipes session context), and Telegram-alerts on an expired login, which no restart can fix. Log: `telegram/watchdog.log`. Added after the bot sat dead-but-alive for a month (2026-07-18 → 08-19); see [docs/telegram-widget.md](docs/telegram-widget.md).

A second watchdog, `telegram/limit-watchdog.sh` (crontab every 2 min, same log), covers **usage-limit stalls**. Claude Code's native auto-resume handles the ordinary 5-hour case, but gives up in three states that leave a detached tmux session parked forever: `stale` ("press enter to continue" — nothing presses Enter on a server), `cap-exhausted` (disarmed after repeated hits), and `horizon-exceeded` (weekly limit, >24 h out). The watchdog sends the Enter, re-sends Claude's own continue prompt, or parks until the weekly reset, and Telegram-alerts each time. It acts **only** on those exact pane strings — never on "session looks idle", which would invent work. It scans every open Claude tmux session (`claude` plus `cl-*` from `/new`), and reads reset epochs from `~/.claude/rate-limit-state/*.json`, written by the statusline. Plan and the string-by-string reasoning: [docs/session-autocontinue-plan.md](docs/session-autocontinue-plan.md).
